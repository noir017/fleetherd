# 子代理（`/super`）

[English](../sub-agents.md) | 简体中文

有些活能拆开：两个仓库要改、一个修复加一次评审、三个问题要分头查。`/super` 让你正在对话的智能体
把活拆开，交给几个智能体同时去干，最后给你一份汇报。你只盯一个话题，而不是四个。

```
/super 把 shop-api 和 shop-web 里的 API 客户端都升级一下，再让 cx 把两边都审一遍
```

## 过程

1. 智能体先看需要看的代码，把活拆成几份。每份交给同一个智能体、各开一个话题，除非你点名了别的智能体，
   或那份活需要别的机器；并写好交给对方的任务。它会要求对方给一份能直接看的回复：结论先行，再给依据，两千字以内。
2. 一张卡片列出每一份：哪个智能体、在哪台机器、指定了模型和设置时是哪些、哪个目录，以及任务全文。**你点 Start 之前什么都不会开始**——
   除非关掉了确认（`/setting delegation off`）：关掉后每一份提出即开跑，卡片随后贴出，列出开了哪些、去了哪个话题，
   没有 Start 按钮。中间那档（`/setting delegation first`）在每个对话里对每个智能体只问一次：
   你在这里确认过它之后，它后面的份直接开跑。两个放宽的档位都只对你自己直接对话的话题生效：子代理自己的话题里，
   `task-new` 仍会出确认卡，所以智能体没法不经过你一层层再开子代理。开着确认时，想改就直接说要改什么，不用点按钮，
   它会重新提一版，新卡片取代旧卡片。改代码的那份把审核一起挂在同一张卡上：谁来审、审核会收到的全文，之后不经过
   派活的智能体自动进行（见[自动审核](#自动审核)）。全量测试在合并前跑一次，不在每一份和每次审核里重跑。
3. 每一份开一个自己的话题，挂在当前话题下面，同时开始跑——每台机器同时最多冷启动四个，其余排队等。
   一个 harness 进程在应答前要花几秒 CPU 和几百 MB 内存，一次全起会把每一份都拖到超时。
   每个子话题的第一条消息写明它来自哪个话题。
4. 某个子代理做完、失败或提问时，派活的智能体会收到通知；它的话题里有一行折叠的 🔔，写明它被告知了什么。
   正常结束一轮的话题标的是「turn ended」而不是「完成」：子代理可能在后台命令还在跑的时候就结束这一轮，
   要不要继续，它写在回复里。
   通知里是子代理的原话——整段回复、整个问题或完整报错，换行保留——放得进卡片额度就全文给出，
   它不用打开子话题就能按结论办事。超过额度的部分会被截掉，并加一行写明原文多长、截在哪里：
   卡片会写明引用的是第几轮，用 `task-read <topic> --turn <n>` 读回那一轮——回复加 `--full` 看全文，
   失败轮直接给整条报错——因为话题里的 ❌ 通知只有开头一小段。按轮号读、而不是按「最后一轮」，
   子话题后来又跑了一轮（常见的是后台补报）也不会读错。一次超过 20 个子代理时，卡片只列前 20 个，
   其余折成一行指向 `fleetherd tasks`。它读每份回复的结论和每次审核的结论，需要时把修改意见
   发回去，不自己看 diff。全部做完后，它写一份汇总，附上每个子话题的链接。

## 和子代理直接对话

子代理的话题就是普通话题：可以打开、阅读、在里面说话、`/stop`。你在里面发起的一轮——或在它跑的时候插进去的话——结束时，
派活的智能体也会收到通知，和它交出去的活一样：通知先引你的原话，标明是你直接对子代理说的，然后才是子代理的回复。
原话超过两千字会截断，并写明截在哪、全文去哪读；附件只列文件名，语音按你确认过的转写文字带。你在那里每聊一轮，
结束时就通知一次，让它掌握你改了什么；几秒之内接连结束的几轮（或和别的子代理的消息）合成一次。你 `/stop` 掉的那一轮不通知，
但你说的话留着，跟这个话题的下一次通知一起带上。只通知直接的上一级：子代理自己开的话题，只通知那个子代理。

要停掉整件活，在发起它的那个话题里点 **Stop**（或发 `/stop`）：会停掉这个话题，以及它派出去、还在干活的所有子代理
（包括子代理再派的）。只要有子代理在干活，即使派活的智能体自己这一轮已经结束，Stop 也会显示。各个会话都保留。

提问：子代理用按钮问的问题等你回答，会置顶到话题列表最上面并推送。只是问「这个任务是什么意思」的，由派活的智能体回答；
需要你拍板的（范围、合并、发版、删除）会转给你。

## 盯着它、纠正它

派活的智能体不用打开子话题就能看到子代理在干什么：`tasks` 会显示它当前跑的工具、这一轮第几步、已经跑了多久、
用了多少上下文；`task-status` 给出一个话题最近三次工具调用。`task-read <topic>` 从会话库里读这个话题，
和 `sessions read` 是同一批行、同一套 `--role`/`--turn`/`--turns`/`--since`/`--grep` 筛选；
`--reply` 给出最近一轮正常结束的回复全文，`--full` 放宽每条消息的截断，`--tail <n>` 只保留每条消息末尾 `n` 行，
跑了一小时的一轮不再是个黑盒。

子代理跑偏时，`task-send --interrupt` 会停掉它当前这一轮，把纠正意见作为下一轮发过去。会话保留：它带着原来的
上下文继续，不是从头再来。不加 `--interrupt` 时，消息只有在支持中途输入的 harness 上才会进入正在跑的那一轮；
否则会等这一轮结束，回执会说明是哪一种。

审核结论不用再手工转述：`task-send <topic> --forward <审核话题> "<要改什么>"` 会把那个话题最近一次正常结束的
回复全文附上，标题写明来自哪个话题、哪一轮。两个话题都必须是这个对话开出来的。在目标话题里，这段回复显示为
可折叠的 **Sub-agent report** 气泡（一行一行，点开看全文）；智能体收到的是全文。和其他 `task-*` 命令一样，
这个只在网页端可用。

## 自动审核

改代码的那份可以在派发时就挂上审核：`task-new --review-by <智能体> --review "<要查什么>"`。审核者和它的任务全文
跟那一份一起列在卡片上，你点一次 Start 两个都算确认过。之后审核不再经过派活的智能体：

1. 那一份每次正常结束一轮、并且目录里有**新提交**时，审核者就收到它的回复，标题写明提交区间
   （`commits 3f2a…..9c1d… on feat/x`）——第一次会在旁边另开一个话题，在同一目录里启动，带上审核任务。
   没有新提交的一轮不触发审核：调研类的活、或停下来提问的，照常通知。
2. 审核者在这一轮结束前跑 `fleetherd task-verdict pass | nits | changes`。
   - `pass`：结束。
   - `nits`：把它的回复转给那一份去改，不再复审。
   - `changes`：打回去；那一份接下来的提交只把增量交给**同一个**审核者——最多 `--rounds` 次（默认 3）。
3. 派活的智能体只收到一次通知，两个话题放在一起：审核通过时，或循环没法自己往下走时——一轮没有新提交或没有回复、
   审核没给结论、轮数用完。失败和提问照常通知。你自己在任何一个话题里说话，或者智能体 `task-stop`，循环就结束：
   这一份交回给你（或智能体）。

循环里网关发出去的只有对方的回复，加一行标题——哪个话题、第几轮、提交区间或结论——不加任何自己的话。每一步都在
派活的话题里显示成一行折叠的 🔁，不会让那里跑一轮；`tasks` 多了一列 `review`，写明每个循环走到哪了。审核者必须
和那一份在同一台机器上。循环持久化在 `<configDir>/review-loops.json`（0600，每次变更原子替换），网关启动时自动恢复
并清理对应话题已不存在的陈旧条目：重启后 `task-verdict` 照常受理，下一批新提交仍自动发给审核者，`tasks` 照常显示循环状态；
被重启打断的那一轮按常规中断轮次处理。

## 侧栏

- 子代理的话题缩进显示在开启它的话题下面。**▾ 3** 可以把它们折叠起来；折叠后，这个按钮显示其中最要紧的状态的颜色
  （有提问、有失败、在干活）。
- 子代理做完的回复和失败不会置顶，也不推送：那些由派活的智能体去读、去汇报。子代理的提问照常置顶并推送。
  它做完时圆点也保持普通的空闲/在线灰色 —— 只有要你去读的话题才亮绿色的「已完成」点，也就是派活那条话题在
  智能体的答复等你的时候。
- 删除一个话题时，它开出的子话题保留下来，变成普通话题。

## 说明

- 只在网页端可用：子话题得挂在你看得见的地方。`/super` 只出现在网页端的命令列表里；在其他平台上手敲，
  网关直接回一句说明，不跑这一轮。
- 网页端会给子代理相关的卡片和子话题收到的任务文本标上 **Sub-agent task**，给 🔔 汇报卡片标上
  **Sub-agent report**。文字本身不变，其他平台按原样显示。
- 不用 `/super`，你让任何智能体把活拆开分出去，它也能提出子代理；任何配置了的智能体都能当子代理。卡片默认要你点。
- `/setting delegation` 有三档。`on`（默认）每次都要点 Start。`first` 在每个对话里对每个智能体只问一次：
  你点过包含它的那张卡片的 Start 之后，同一个对话里再派这个智能体就直接开跑；一批里既有确认过的也有新的，
  确认过的直接开跑，新的仍然上卡片。这份记忆只在网关进程里、按对话保存，重启或换一个对话会重新确认；
  改动这个设置（不论往哪档改）也会清空。`off`（或 `delegation.confirm: false`）会让智能体一提子任务就开跑，卡片随后作为记录贴出。
  三档都只对你自己直接对话的话题生效——子代理自己的话题每次都仍然要确认。只有你能改，任何智能体命令都碰不到它。
- 网关之外的调用方也能经 [MCP 入口](external-mcp.md)、从它自己的话题提议子任务。它的卡片不管这个设置怎么设，都要等你点 Start。
- 某一份可以换成该智能体 `/model` 列表里的另一个模型：你要求了，或者那份活明显需要（`task-new --model`）。
  卡片上会写明模型，因为模型决定这份活花多少钱。智能体没有的模型在提出时就被拒绝；开跑时切换不过去的，
  那一份算失败，原因写在它的话题和卡片上——绝不悄悄换成别的模型跑。这个话题之后一直用这个模型，
  就像在里面用 `/model` 选过一样。
- 某一份也可以选该智能体自己的设置——就是它的设置开关里提供的那些，比如它用哪个账号干活
  （`task-new --option account=alice@example.com`，多个写成 `key=value,key=value`）。卡片上紧跟在模型后面列出。
  智能体没有的设置或取值在提出时就被拒绝，并列出它实际提供的选项和说明（比如某个账号的额度）；开跑时被智能体拒绝的，
  那一份算失败，写明原因——绝不悄悄用默认设置跑。模型归 `--model` 管，不归 `--option`。
- **独立 git worktree（`task-new --worktree [<名称>]`）**：多份任务改同一个仓库时，传 `--worktree`（可指定名称，
  省略时按 `--title` 生成 slug）会让网关在执行那一份的机器上、以仓库当前 `HEAD` 切出新分支 `<名称>` 并创建
  `<仓库根目录>/.worktrees/<名称>`，再让子代理在那里启动。提议时只做只读校验（非 git 目录、已存在的 worktree
  或分支都会当场拒绝），真正开跑时才创建；确认卡片会提前列出计划的路径和分支。若 `.worktrees/` 尚未被忽略，
  网关会写入 `.git/info/exclude`，绝不改受版本控制的 `.gitignore`。已创建的 worktree 持久化在
  `<configDir>/worktrees.json`，每 15 分钟定期巡检一次：只有当分支已合入来源分支、工作区无未提交或未跟踪改动、
  该话题当前没有轮次在跑或等提问、且上一轮结束已满 1 小时这四个条件同时满足时，才会执行不带 `--force` 的
  `git worktree remove` 和 `git branch -d` 并记录日志；其余一律保留，并在 `fleetherd tasks` 的 `worktree` 列展示。
- 智能体提议前可以先查某一个智能体：`task-agents <智能体>` 列出它的模型（标出默认的那个）、每个设置的全部取值和它对每个取值的说明、
  它的权限级别、此刻有几轮正在它上面跑，以及它是否正因用量上限在冷却。查询要起一个它的会话来问（不跑任何提示词），
  冷启动的智能体要等几秒；不带参数的 `task-agents` 只读配置，列出全部智能体。
- 智能体分布在多台[机器](remote-hosts.md)上时，只有需要别的机器的那份才放过去；其余的留在它自己这台机器上，
  那里的代码目录和工具都一样。放到别的机器上跑的那份，卡片上会标 `@ <主机>`。
- `/super` 是网关链接到每个智能体 skill 目录里的一个 skill，和 `fleetherd` 那个放在一起。Claude Code 把它当成命令；
  Codex、OpenCode、Antigravity 靠它的描述来识别。`gemini`、`dsh` 这两种 harness 拿不到网关的 skill，
  在那里用 `/super` 会回复不支持。
- 网关重启打断了子代理的一轮时，会在子代理自己的话题里说明，派活的智能体不会收到通知。
